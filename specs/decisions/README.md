sequential and immutable; supersede rather than edit an `Accepted` decision.

0049 is deliberately absent: it recorded a pathfinding experiment on the map's
geometry that was removed rather than kept, and the record went with it. The
number is retired, not free. It stays retired: [0062](./0062-a-travel-graph-of-zone-lines.md)
routes between zones over the mapmakers' **exit labels**, which is different data
with a different provenance, and still does no routing inside one.

Downstream it was a hole: attribution keys off `attacker`, so every tick — which on a DoT is nearly all of its damage — landed in a phantom row named after the spell, out of `yourDealt`, out of the DPS, out of the spell's own total, and unable to engage the fight scope. - [0072: A folder of maps is named once and remembered](./0072-a-folder-of-maps-is-named-once-and-remembered.md) — *ADR 0061 settled what a folder's gazetteer is and left "every launch, synchronously, on the main process" as when. The map window asks for names on mount (a zone name is what resolves your zone to a map file) and asks twice — the chosen pack, plus the game's own maps it borrows from per ADR 0063 — and it's restored at launch, so a real install read **199 MB across 1,321 files** and held the main process ~0.8 s warm, with the reads themselves saturating the disk queue. Nearly all of those bytes are `L` geometry that naming never looks at, but the base files can't simply be skipped: the game's own maps keep their exit labels there, and dropping them loses 24 names of 54. So the answer is to pay it **once** — each folder's gazetteer stored in `userData` against a signature of file count, total bytes and newest mtime — and, when it must be paid, to pay it as background work: one shared `readFolderPois` reading a few files at a time off the main thread, sieving `P` lines out of the raw bytes rather than decoding and splitting 199 MB. A worker thread was rejected as the wrong size for something that now happens once per pack per install*

- [0073: A click-through window keeps its chrome](./0073-a-click-through-window-keeps-its-chrome.md) — *the working click-through ADR 0032 said should replace the dead setting it deleted. Both floats get a per-window 👻 toggle beside the pin, and the mode has a hole in it: each window marks exactly **one** pass-through region (the list's panel, the map's canvas) with `PASS_THROUGH`, and everything else — title bar, tabs, toolbar, open side panels — stays a window, which is what keeps the mode escapable. `useClickThrough` watches the cursor and flips `setIgnoreMouseEvents(…, { forward: true })` at the crossings; `forward` is the trick, since mouse **moves** still reach a window that can't be clicked. ADR 0035's mechanism and ADR 0045's lend-it-a-click, generalised from "for one moment" to "region by region". A press holds the window, so a drag off the title bar isn't dropped; only moves are forwarded, so the region is a glance and not a surface — no scrolling, no zooming, hover intact*

- [0074: How a window was left is window state, not a setting](./0074-how-a-window-was-left-is-window-state.md) — *the three title-bar toggles had ended up in three different homes, none of them where the window's own size and position live: **pin** in `overlay.alwaysOnTop` (app-wide, for a per-window fact — so the map kept a second copy in `localStorage` and corrected itself a frame after opening, its pin decided by the **main** window's setting until then), **◐ opacity** nowhere at all (transient by design; every restart quietly undid a window you wanted solid), **👻 click-through** in `localStorage`. They're all the same kind of fact — the condition one window was left in — so they join bounds and maximized in `window-state.json` as `WindowToggles { pinned?, opaque?, clickThrough? }`, applied by **main when it creates the window** (opacity in the constructor via `windowOpacity`, the one rule both ends share) and owned by the renderer after, through a single `useWindowToggle`. Nothing is applied before the saved value arrives, which is the flash this removes. `overlay.alwaysOnTop` is deleted per ADR 0032's precedent and `applyOverlaySettings` with it — settings now push nothing onto a window. Remembering and applying stay separate channels, because click-through flips many times a second as the cursor crosses, and those are moments, not choices*

- [0077: A pet is proven, not guessed](./0077-a-pet-is-proven-not-guessed.md) — *ownership was read off the log's possessive (`Kainos`s warder`), which works only while a pet's name contains its owner's. A **named** pet writes `Garn hits a coyote` — identical to a player — so [0067](./0067-the-meter-counts-your-party-s-fights.md)'s scope saw neither side as ours and **dropped the fight whole**: the damage went missing, not onto the wrong row, and a meter that is merely low looks like a quiet evening. - [0078: A fight records why it ended](./0078-a-fight-records-why-it-ended.md) — *[0036](./0036-a-fight-ends-on-death-not-a-lull.md) already tells a **resolved** fight (something died, short quiet closes it) from an unresolved one (enemy still up, long silence needed), computes which applied on every line, and throws the answer away — so 90 seconds ending in a kill and 90 seconds ending because the log went quiet read identically, though only one of them finished. Now stamped as `kill` / `death` / `timeout`, with the **later** of a kill and a death winning when both resolved it, plus `cut` for a fight the log didn't end at all (a reset, a flush). `cut` exists as a value precisely so **absent** can keep exactly one meaning — stored before this was recorded ([0021](./0021-stored-fights-keep-their-source.md)). - [0079: An unread line is counted by its shape](./0079-an-unread-line-is-counted-by-its-shape.md) — *a line no matcher claims is dropped in silence, and our tests can only pin grammar we already thought of — the same silence that left [0020](./0020-split-by-stance-and-invocation.md) dark against 243 stance lines that parsed fine and which nothing listened for. Unread lines are now tallied **by shape** (digits fold to `#`; nothing cleverer, since over-folding hides the gap), capped, reporting what it turned away so a truncated list can't pass as complete, and printed through `logging.ts` after a replayed gap. The half that makes it readable is the second bucket: chat, tells and other players' emotes are **matched and ignored** — counted, text discarded — so an evening of guild traffic can't bury the one line that reveals a hole, and the bulk of other people's words are never kept in the first place. Names are **not** folded and the ADR says so rather than over-claiming. Relatedly, the two hand-maintained "which kinds are combat" lists become one typed `isCombatEvent`, so omitting a new kind is a compile error instead of a silence*

- [0080: The game's own spell file](./0080-the-game-s-own-spell-file.md) — *the log says what you cast and what it did, never what it **cost**, so the most useful question a caster has was the one the meter couldn't answer. So a contributor gets an **id** — minted once per install, its own file, `{id, name}` where the name is a label and the id is the key — and reading one off a payload **fails closed**, since accepting a name as a key costs the property that makes a key worth having. Deliberately not the awari peer id, which [ADR 0015](./0015-peer-presence-via-hello.md) keeps per-session: that identifies a connection, this identifies a source of data we keep — and it rides only on the contributed payloads, never on `hello`, so connecting without sharing broadcasts nothing stable. One store factory (`contributions.ts`) holds the five rules both peer stores want — keyed by id, a report replaces, an **empty report keeps what it taught** ([ADR 0056](./0056-a-dropped-record-keeps-what-it-taught.md)), arrivals vetted with the impossible discarded rather than clamped, capped per contributor — and shared kills become a store of their own, safe to keep precisely because a shared kill carries no time and no loot, so a bad one can only misplace a dot. **Main files contributions, not a window.** Trust is `pooling.ts`: provenance **shown, not scored** (by kills, not by heads), `myCount` carried per drop so a pooled rate splits back into yours and theirs, and a plain disagreement **reported, not resolved** — with no per-peer trust score, which would be a made-up number wearing an authoritative face. The old name-keyed file is re-keyed to `name:bob` rather than dropped: months of other people's kills aren't thrown away to tidy a key*
- [0121: A mob is a range of levels, so its bounds widen](./0121-a-mob-is-a-range-of-levels.md) — *"a gnoll pup" is not level 5; the pups in that camp are 4 to 6, and the wiki writes exactly that (`Level: 33-37`). So the thing being estimated is a **range**, and `estimates.ts`'s first rule runs backwards: `tighten` on a level produces a figure that looks reasonable and **excludes the truth** — con a pup at 4 then at 6 and a tightening lower bound says "at least 6" about a mob you have seen at 4. Hence `widen`, `tighten`'s mirror, with the distinction named in both: a **constraint** has one true value and narrows inward, a **containment** has none and opens outward. Every other rule carries over unchanged, which is the argument for their being rules — an implausible reading is still discarded rather than clamped (a containment can no more recover from a bad value), the sample count is still part of the figure (one consider is a sighting, not a range), and the wiki is still reconciled by **overlap rather than equality**, since our range is built from however many considers were typed. Pooling a peer's range is safe in a way pooling their rate isn't: the worst a wrong one does is make ours too wide, which reads as "we're not sure". **The live source is not yet wired** — reading a level off a consider needs the wording this server prints, and `parseSighting` fails closed on purpose*
- [0122: A zone wears its levels, as the wiki wrote them](./0122-a-zone-wears-its-levels.md) — *the hunt says where to go and had nothing to say about whether you survive it: a level-8 character's list puts Lower Guk and Greater Faydark in the same column, sorted by how much of the list each covers. eqlwiki answers it on the same infobox, on the same pages, that [0117](./0117-the-wiki-says-which-zones-touch.md) already crawls — a **Level of Monsters** row, written by people who play here. So it is one more row off an existing crawl rather than a new source, and the crawl itself moved into `scripts/lib/eqlwiki.mjs` (category listing, wikitext fifty pages a request, infobox row reader) with the adjacency generator rebuilt on it and producing its table **byte for byte unchanged**. The judgement is **verbatim, never resolved into a span**: `1-20, 35` flattened to `1-35` asserts Butcherblock holds levels 20 through 34, which is exactly what the wiki took the trouble not to say, and `29-34 Droga Main, 33-38 Inner Sanctum` is two bands *and* where each one is. Same instinct as [0121](./0121-a-mob-is-a-range-of-levels.md) one level down — a spread is the honest shape of "what level is this". The only thing judged is whether a digit is present at all, since `?` and `Quest Only` shown beside a zone name would read as information. **Shipped, not fetched** (`zones/levels.generated.ts`, `npm run zones:levels`), like the tables beside it. Looked up through the shared resolver with `exact`, `order`, `typo` and `narrower` — the names in hand come from item pages, map packs and the log — but **`fuzzy` refused**, because this figure reads as *what you are walking into* and the nearest spelling is not reason enough to hang one zone's danger on another; stricter than the expansion badge next door, whose worst case is a mislabel ([0068](./0068-a-zone-name-resolves-against-what-we-know.md)). A page-title qualifier comes off first — `Cazic Thule (Zone)` disambiguates the god, `(Pre-Revamp)`/`(Post-Revamp)` are one Chardok — while the answer still names the page it came from, since the loose tiers mean it can differ from the name asked for. **99 of 116 zones carry a range**; the 17 silent ones are the cities and the tutorial, which is the right silence rather than a gap. It stays a claim: the hover says the zone's own page, not our kills, and nothing reconciles it against what has been fought there. Rejected: parsing to `{low, high}` (wrong for every multi-band zone), colouring it against your level (the app does not know your level well enough to gamble a corpse on, and a banded range has no single number to compare), and sorting the hunt by it (the hunt is sorted by how much of your list a zone covers, which is what you asked it)*
- [0123: A popover is placed in the units it is written in](./0123-a-popover-is-placed-in-the-units-it-is-written-in.md) — *the hover card's placement rule was already right and already tested — beside the name, never over it — and it still landed on the link, reported from Search and true app-wide. Both faults were in what the rule was **given**, and both were measured rather than reasoned about. The interface scale is a CSS `zoom` on the root ([0041](./0041-interface-scale-is-a-css-zoom-per-window.md)), so every window has **two pixel spaces**: what you measure (`getBoundingClientRect`, `clientX`, `innerWidth`) is real screen pixels, what you write (`left`, `top`, `max-width`) is multiplied by the zoom on the way in — measured, a `fixed` element given `left: 200px; top: 100px` at zoom 0.6 reports its corner at (120, 60). A card placed from its own measurements therefore appears at *scale* of where it was aimed, and since the overlay's scale only ever shrinks ([0026](./0026-interface-scale-only-shrinks.md)) the error is always **toward the name**: at 80% and 60% it sat on the word it was explaining. And the anchor was the element's box rather than its **words** — a list row's name is a stretched flex item, 393px of box around 122px of text — so "beside" was nowhere and every hover in every list fell to the last resort, below the name, which is the one placement a *list* can't afford because it covers the rows either side of the one you pointed at. That hid a third fault: the card was measured where it was *guessed* to go, and one aimed past the right edge has no width to shrink into, so it measured as a one-word column. So: **convert once, at the boundary** (`lib/screen.ts` — `localView`, `localSize`, `localTextBox`, `localPoint`), after which nothing downstream knows the scale exists; **anchor to the words** (a range over the element's contents, clamped to it); and in a narrow window **get narrow rather than move** (`besideWidth` caps the card to the roomier side, applied as `--tip-avail` against the stylesheet's own `--tip-want`, so how wide the card *wants* to be stays with the rest of its look). Verified over a real results list at 100/80/60%: before, below in all twelve hovers and on the name in eight of them; after, beside it in eleven, on the name in none. The map's cursor tip was misplaced the same way (up to 2× there) and converts through `localPoint` now. Left alone: the pin editor, which writes a click's raw `clientX/clientY` — same defect, but a click-positioned editor is not a hover popover. The trap left behind is ADR 0041's `vh` trap in another shape — **anything that positions itself from its own measurements must convert them first***
- [0124: Lucy is a second opinion, asked last and quoted rather than believed](./0124-lucy-is-a-second-opinion.md) — *[ADR 0103](./0103-search-can-answer-from-your-own-log.md) closed the hole where eqlwiki has no page and your **log** does; it left the one where neither has — a name you have merely *seen*, on a corpse someone else looted or a tooltip in a screenshot — and, for a name the log does know, the fact that a loot ledger can say you held one and never what slot it goes in. [Lucy](https://lucy.allakhazam.com) is Allakhazam's **Live EverQuest** item database and covers exactly that: the in-game tooltip verbatim, every mob known to drop it and every merchant known to sell it — `Rusty Short Sword` has a full card and **166 sources** there. It is also a source about a *different game*, further from this build than eqlwiki is, whose catalogue is mostly items that cannot exist here. So: **third rung, asked only where the first two returned nothing**, under a heading that says so, and a row that **opens rather than adds** — adding on the strength of a source not yet asked about the era is the mistake the era badge exists to prevent. **Era is derived**, because Lucy has no era or expansion field anywhere (not even in the 300-column raw dump): the only signal is the zones on its source rows, matched against the gazetteer of zones this server runs ([0076](./0076-a-supplied-gazetteer-outranks-our-guesses.md)) — one placeable zone is in era, zones with none placeable is out, **no zones at all is `unknown` and shown as unknown**, which is the common case and is *not* hidden by the era toggle, since hiding what you couldn't judge is how a filter starts lying. Reading Lucy's zone names needs its own vocabulary (`[RoS]`, `West Freeport 2.0`, `Ruins of Old Paineel 2.0 (The Hole)` — where the gloss is the only placeable half), which is [0057](./0057-a-grade-is-not-an-identity.md) in a third source's handwriting. Politeness is designed in rather than hoped for: **a month's cache for an item and a week's for a search including an empty one** (this client caches misses, because it is only ever asked about names that already failed), **nothing fetched unasked** (a search is one request, opening an item is one, and every other appearance reads cache only), a shared `polite-queue.ts` serializing requests a second apart, and **the cookie fetched up front** — the obvious ask-then-handshake was written first and does not work, because CloudFront caches on the URL and ignores the cookie, so the cookieless first request caches *the refusal* under the URL you wanted and the retry is served your own poison. `Water Flask`'s 54 mobs and **362 merchants** are capped at 50 rows, but the verdict is computed over all of them first (a cap can never flip an item out of era), placeable and killable rows are kept first, and the real total is shown. **"Sold by" is the sleeper win**: the best answer to "where do I get one" is sometimes "don't kill anything, go and buy it". Rejected: resolving era per search hit (twelve fetches per query, on the query shape that is by definition a miss), guessing era from item id or `reqlevel` (a cheap guess dressed as a filter is worse than "unknown"), and folding Lucy's loot into `drop-truth.ts` — that module's output is a rate measured on **this** server, and a third game's drop table has no business in it. Two more ways to be wrong, both erring towards showing something questionable rather than hiding something real*
- [0125: A hunt is two questions, so the page turns round](./0125-a-hunt-is-two-questions.md) — *zone → mob → items answers "I'm going to Lower Guk, what does that get me?", which is the right answer once the destination is decided and the wrong shape for the question a shopping list asks first: **"I need a Fire Emerald — where is it likeliest to drop?"** An item off four mobs in four zones appeared in four separate blocks, each with its own rate badge, so comparing them meant scrolling, remembering percentages and doing the sort by eye — the rates were already on screen and only the arrangement stopped them being usable. So a **`By zone` / `By item` toggle**, with by-item **inverting the built hunt** (`huntByItem`) rather than re-reading the sources, so the zone filter and every rule `buildHunt` applies hold in both views by construction. **The filter follows the grouping, in one control**: the zone picker plus *follow* by zone, and the same picker turned into a **search over the items on your list** by item — where the view deliberately looks **everywhere**, since narrowing to a zone is meaningless in a view whose entire answer is *which zone*, and an item filter is meaningless in one that lists a zone. A swap rather than a second box: the row has only so much room, and a filter that does not apply to what you are reading is worse than no filter. The item pick is **not remembered** (the zone pick is, because you stay in a zone for an hour) — an item you finish leaves the list, and a filter that outlived it would open on an empty page. Places sort by **rate, then zone** — zone breaking the tie rather than mob name, because two mobs in one zone is one trip and what you can farm without moving should read as one block. An **unmeasured place sorts last, not as zero**: "nobody has measured this" and "this never drops" are different claims, and it shows a dimmed `—` rather than nothing, since in this view the rate is the column everything is ordered by and an omitted one would read as *no chance* while sitting at a position it never explains. **The rate that sorts is the rate that shows** — `bestRate` now returns its numeric `value` beside the text, so ordering and badge come from one decision about which source leads ([0025](./0025-observation-over-the-wiki.md)); a number derived beside the caller could sort by the wiki's figure under badges showing yours. **Items are listed by name, not by best rate**: a rate moves every time you kill something, and a self-reshuffling list has to be re-read from the top after every drop — the ordering that answers *where do I farm this* belongs inside an item, among its places. A **named mob keeps a section of its own**, having no item to be grouped under and otherwise vanishing from the page it was added to ([0098](./0098-a-mob-is-a-thing-you-hunt.md)). The choice is remembered per window and defaults to `zone`. The two views now share their reconciliation, their zone label (name · wiki level range · "you are here") and their rate badge, since a drop reading one way in one view and another in the other would be two claims about one mob's loot — and the by-item view is the one that makes a **thin sample visible**, four places for one item with three wiki figures and one of yours out of nine kills being a comparison the zone view never put side by side. Rejected: **replacing** the zone view (that question is the one you ask while standing in the zone, which is when the tab is open), sorting items by rate, showing **only the best place** (a 2% drop where you are standing beats a 6% across the world, and the app can't weigh that for you — so every place is listed, best first, with the zone's level range right there to judge against), treating a missing rate as 0%, **keeping the zone filter alive in the by-item view** (silently worst of all — a page filtered by a control that is not on screen looks like a page missing half its answer), and a **free-text filter box** in place of the picker (which only ever offers names that are on the page, and keeps the chosen one visible, where a typed fragment matching nothing looks identical to a list with nothing in it)*


## Open Questions

- A zone states what level its monsters are, and we never check it
  ([ADR 0122](./0122-a-zone-wears-its-levels.md)). `mob-knowledge` is accumulating observed level
  ranges per mob ([ADR 0121](./0121-a-mob-is-a-range-of-levels.md)), so "the zone's page says 30-45
  and you have conned five things here at 12" is a comparison we could make — the same
  report-don't-resolve shape as a drop rate. Worth surfacing, or is a zone's range too coarse a claim
  to be contradicted by whatever happened to be conned in one camp?

- Should a **group-mate's** drop reach your overlay? [ADR 0105](./0105-a-tracked-item-says-so-when-it-drops.md) can only speak about **your** loot, because that is all the log ever names — and the request it came from was "tell me when one of *us* loots it". The room already carries pooled observations ([ADR 0024](./0024-mob-knowledge.md)) and per-peer kill locations, so a `loot` message kind is small; what needs deciding is everything around it. Whose list does an arriving drop credit — nobody's, or the asker's, given [ADR 0027](./0027-only-your-kills-count.md) says only your own kills count for you? It is a **privacy default** in the same family as `shareLocation`, and a louder one: a location is where you are, a drop is what you have. And it can only ever be partial, since a peer not running the app is invisible while sitting in the same group — which makes silence indistinguishable from "they didn't loot it".

- **Can a celebration exist without a number to beat?** The scoreboard
  ([0093](./0093-a-high-score-is-a-personal-best-with-a-floor.md)) is built entirely on *magnitude*: a
  category, a figure, a floor, and a previous value to clear. A sweep of a real log turned up two
  moments that plainly deserve a banner and have **no figure at all** — `You have been knocked
  unconscious!` **survived** (26 knockouts in three weeks, 4 of them lived through), and killing a
  **named** (27 distinct). Neither is a personal best; both are the best stories in the log. Either the
  board grows a second kind of row — a *moment*, counted rather than measured — or these belong to a
  separate feed and the scoreboard stays strictly about magnitudes. Worth settling before either gets
  built, because the answer decides whether `HighScore` gains an optional value or a sibling type does.
  Both candidates are written up in [ideas.md](../ideas.md) `## More high scores`.

*The three below came out of reading the other EQ Legends tools ([neighbours.md](../neighbours.md));
the work they'd unblock is in [todo.md](../todo.md) `## From the neighbours, second pass`. The
fourth — whether to read installed game files beyond `maps/` — was **settled by
[ADR 0080](./0080-the-game-s-own-spell-file.md)**: yes, bounded to the columns a patch can't move,
and degrading to blank facts when the file isn't there.*
- **Is a second reference source worth taking from a different game?**
  [ADR 0003](./0003-eqlwiki-runtime-data-source.md) chose eqlwiki because it is *this* game's wiki. The
  Project Quarm distillation a neighbour ships is richer than the wiki on the three things we most want
  seeded — named spawn points, respawn timers, drop percentages — and is EQL's lineage rather than EQL.
  [ADR 0025](./0025-observation-over-the-wiki.md) already says observation outranks the wiki, so the
  machinery for "shown as a claim, overruled by what you saw" exists. Against it: the wiki is at least
  *edited by people playing this game*, and a wrong number from a sibling game is wrong in a way no
  amount of careful labelling makes the player's problem less annoying. Also a licensing question, not
  just a design one.
- **Does a dungeons-only guide line reopen in-zone routing?** ADR 0049 was retired and
  [ADR 0062](./0062-a-travel-graph-of-zone-lines.md) narrowed the map's non-responsibility to "no
  routing inside a zone", because an `L` record is a wall in a dungeon and a contour outdoors, so a
  drawn route is a guess dressed as advice. A neighbour ships one anyway and it doesn't refute the
  objection — it paths *along the drawn lines*, which parallels a corridor and traces a hillside. But
  the objection is really about *outdoors*: where the geometry is known to be walls, the guess is
  sound. If we end up reading `spells_us.txt` we get `zone_type` (outdoor/dungeon) for free. Is a route
  that refuses to draw outdoors a different enough claim to be worth costing, or does a feature that
  works in half the world read as broken in the other half?
- **Should interface scale grow as well as shrink?**
  [ADR 0026](./0026-interface-scale-only-shrinks.md) caps at 100% — the overlay's job is to take less
  of the screen, and a magnified overlay is a bigger thing between the player and the game. Two
  neighbours ship the opposite hard: presets at 100 / 200 / 250%, with layouts that grow rather than
  clip, offered in the same menu as the theme. They are serving the same players we are, and EQ's
  audience is twenty-five years older than it was. Is our cap a considered stance or an untested
  assumption?

- **OCR beyond item lookup — is a live health trace wanted?** It's ruled out for the **experience
  bar** (the log's gains plus a level-up baseline solve it exactly,
  [ADR 0017](./0017-camp-efficiency-and-asking-the-player.md)) and for **mana cost** (the wiki states
  it — see [ideas](../ideas.md)), and **maximum health** is now *inferred* from what you survive
  ([ADR 0018](./0018-inferred-max-hit-points.md)). So the only prize left is a health trace rather
  than a maximum, and it needs a user-calibrated screen region per UI layout, is fragile across
  resolutions and UI mods, may capture nothing in exclusive fullscreen, and a confidently wrong
  reading is worse than a blank.
- **Items per kill, alongside the drop chance.** `drops` counts kills that produced an item, which is
  the right numerator for a probability but throws away the stack size — "You looted 2 Spiderling
  Eye" counts once ([ADR 0024](./0024-mob-knowledge.md)). For a stackable trash drop the useful
  figure is items-per-kill. It's a second number rather than a correction, and it changes the shared
  observation shape, so it wants deciding rather than sneaking in.
- The app now reports its peer connection truthfully, but **nothing displays it**
  ([ADR 0070](./0070-a-dropped-room-rejoins-itself.md)): the map's `connected` is the
  `connectPeers` *setting*, and the only consumer of the real status is the room clearing itself.
  During an outage a player sees the user list empty and their pings stop landing, with nothing
  saying why. Is that worth a real connection light, or is a silent self-heal the right amount of
  noise for a game overlay?
- A recovering peer re-joins under a **fresh peer id**, so the room sees a stranger arriving rather
  than a return ([ADR 0070](./0070-a-dropped-room-rejoins-itself.md), on ADR 0011's "the id is
  transport-only"). Cheap today; if reconnects prove frequent it reads as churn in the 👥 panel.
  Should a session keep its id across a recovery?
- A succor point can be **read** off a map and never written down
  ([ADR 0069](./0069-a-succor-is-a-port-inside-one-zone.md)), because `TravelPlace` carries no
  coordinates and an unplaced safe point is a guess that can beat a measured walk. Should a
  hand-authored place be able to state a `/loc` — which would also let `manual-links.ts` place the
  docks it currently has to invent?
- The `fuzzy` tier of `resolveZone` currently fires on **nothing** across all 344 shipped zones
  ([ADR 0068](./0068-a-zone-name-resolves-against-what-we-know.md)) — every name it could reach,
  the three tiers above it already reached. Is a last resort that has never spoken worth carrying,
  or should it wait until a source we don't yet read gives it something to do?
- Should the Damage tab **say** whose fights it's counting — a line naming the party it
  believes you're in ([ADR 0067](./0067-the-meter-counts-your-party-s-fights.md))? The filter is
  always on and silent, so a group line the server words differently than we expect looks like
  a meter that's merely quiet about a group-mate. Against it: the roster is evidence, not truth,
  and showing it invites reading it as the game's own group window.
- A line watch is a substring of the whole log line, and nothing rate-limits it
  ([ADR 0050](./0050-a-watch-can-read-a-whole-log-line.md)). A careless one ("hit") fires
  thousands of times a night. Is the overlay's four-banner cap enough, or does a watch want a
  cooldown — and if so, per watch or per matched sentence? Two later decisions sharpen it without
  answering it: a delay ([ADR 0082](./0082-an-alert-can-be-scheduled.md)) means such a watch now
  *queues* its noise instead of merely making it, and conditions
  ([ADR 0084](./0084-a-watch-is-a-rule-not-a-substring.md)) give a careless watch a way to be
  narrowed rather than throttled — so a cooldown would have to say whether it gates the match or the
  firing, and whether narrowing is simply the better answer.
- Open Relay's community TURN is best-effort and not production-grade
  ([ADR 0046](./0046-our-own-ice-servers-not-peerjs-defaults.md)). Is peer sharing worth
  running our own TURN for, or is "works for most, fails for symmetric NAT" acceptable?
- Pooled mob knowledge is attributed and forgettable, but unweighted: every peer counts the
  same. Should contributions be weighted, or individual peers mutable/vetoable?
  See [ADR 0024](./0024-mob-knowledge.md). **Now answerable**: contributions have a stable key to
  hang a weight or a veto on ([ADR 0120](./0120-a-contribution-is-keyed-by-who-made-it.md)), and
  `forgetPeers(id)` already drops one contributor. What is still undecided is whether a *weight* is
  honest at all — ADR 0120 argues a per-peer trust score would be a made-up number wearing an
  authoritative face, and that showing provenance and reporting disagreement is the truthful
  version. A per-contributor **mute** is the narrower question left: it needs no invented number.
- What should a contributor be, when one person plays three characters
  ([ADR 0120](./0120-a-contribution-is-keyed-by-who-made-it.md))? The id is per **install**, which
  matches where the data comes from — one kill log, one machine. It also means the same person on a
  second PC is two contributors, and a shared machine is one. Neither is wrong, and nothing yet asks
  the question sharply enough to settle it.
- Coin per mob pools with peers; an item's vendor price does not
  ([ADR 0047](./0047-money-is-copper-in-two-ledgers.md)). A price is the easiest thing of all to
  pool — it's the same for everyone, so one observation settles it — but it isn't in the
  observation payload. Worth adding, or is "what you've sold yourself" the honest scope?
- A zone's difficulty rides inside its name, which keeps it out of the stored shapes and the peer
  payload ([ADR 0057](./0057-a-grade-is-not-an-identity.md)). Now that a variant is no longer its
  own sample ([ADR 0059](./0059-a-zone-s-variants-are-one-zone.md)), a camp report that wanted to
  compare difficulties would have to read them off the *records* before they age out. Is that worth
  a field of its own, or is "Blackburrow 3" in the name enough for a player reading their own
  history?
- Undocumented drops are surfaced per mob. Should they also be *reported upward* somewhere —
  a shared list of "things this build drops that no wiki knows"? The room already pools
  observations ([ADR 0024](./0024-mob-knowledge.md)); this would be the useful summary of them.
- Should out-of-era pages be *hidden* (not just badged)? Filtering search results by
  era would need a category lookup per result — flagging-on-open is done today.
- Should the overlay support multiple named lists / profiles per character?
- Should the damage meter break a fight down by *phase* (adds arriving, mob enraging)?
  Today a fight is one flat window from first swing to last.
- Should a fight's stored record keep the raw `logId` range it covered, so a past fight
  could be re-derived from the log if the tracker's maths changes?
  See [ADR 0019](./0019-parse-once-and-one-tracker.md).
- Should the overlay toggle hotkey be user-configurable? (Currently a fixed
  `Ctrl/Cmd+Shift+O` via Electron's built-in `globalShortcut` — no native dep.)
