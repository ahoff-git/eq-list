sequential and immutable; supersede rather than edit an `Accepted` decision.

0049 is deliberately absent: it recorded a pathfinding experiment on the map's
geometry that was removed rather than kept, and the record went with it. The
number is retired, not free. It stays retired: [0062](./0062-a-travel-graph-of-zone-lines.md)
routes between zones over the mapmakers' **exit labels**, which is different data
with a different provenance, and still does no routing inside one.

Downstream it was a hole: attribution keys off `attacker`, so every tick — which on a DoT is nearly all of its damage — landed in a phantom row named after the spell, out of `yourDealt`, out of the DPS, out of the spell's own total, and unable to engage the fight scope. - [0072: A folder of maps is named once and remembered](./0072-a-folder-of-maps-is-named-once-and-remembered.md) — *ADR 0061 settled what a folder's gazetteer is and left "every launch, synchronously, on the main process" as when. The map window asks for names on mount (a zone name is what resolves your zone to a map file) and asks twice — the chosen pack, plus the game's own maps it borrows from per ADR 0063 — and it's restored at launch, so a real install read **199 MB across 1,321 files** and held the main process ~0.8 s warm, with the reads themselves saturating the disk queue. Nearly all of those bytes are `L` geometry that naming never looks at, but the base files can't simply be skipped: the game's own maps keep their exit labels there, and dropping them loses 24 names of 54. So the answer is to pay it **once** — each folder's gazetteer stored in `userData` against a signature of file count, total bytes and newest mtime — and, when it must be paid, to pay it as background work: one shared `readFolderPois` reading a few files at a time off the main thread, sieving `P` lines out of the raw bytes rather than decoding and splitting 199 MB. A worker thread was rejected as the wrong size for something that now happens once per pack per install*

- [0073: A click-through window keeps its chrome](./0073-a-click-through-window-keeps-its-chrome.md) — *the working click-through ADR 0032 said should replace the dead setting it deleted. Both floats get a per-window 👻 toggle beside the pin, and the mode has a hole in it: each window marks exactly **one** pass-through region (the list's panel, the map's canvas) with `PASS_THROUGH`, and everything else — title bar, tabs, toolbar, open side panels — stays a window, which is what keeps the mode escapable. `useClickThrough` watches the cursor and flips `setIgnoreMouseEvents(…, { forward: true })` at the crossings; `forward` is the trick, since mouse **moves** still reach a window that can't be clicked. ADR 0035's mechanism and ADR 0045's lend-it-a-click, generalised from "for one moment" to "region by region". A press holds the window, so a drag off the title bar isn't dropped; only moves are forwarded, so the region is a glance and not a surface — no scrolling, no zooming, hover intact*

- [0074: How a window was left is window state, not a setting](./0074-how-a-window-was-left-is-window-state.md) — *the three title-bar toggles had ended up in three different homes, none of them where the window's own size and position live: **pin** in `overlay.alwaysOnTop` (app-wide, for a per-window fact — so the map kept a second copy in `localStorage` and corrected itself a frame after opening, its pin decided by the **main** window's setting until then), **◐ opacity** nowhere at all (transient by design; every restart quietly undid a window you wanted solid), **👻 click-through** in `localStorage`. They're all the same kind of fact — the condition one window was left in — so they join bounds and maximized in `window-state.json` as `WindowToggles { pinned?, opaque?, clickThrough? }`, applied by **main when it creates the window** (opacity in the constructor via `windowOpacity`, the one rule both ends share) and owned by the renderer after, through a single `useWindowToggle`. Nothing is applied before the saved value arrives, which is the flash this removes. `overlay.alwaysOnTop` is deleted per ADR 0032's precedent and `applyOverlaySettings` with it — settings now push nothing onto a window. Remembering and applying stay separate channels, because click-through flips many times a second as the cursor crosses, and those are moments, not choices*

- [0077: A pet is proven, not guessed](./0077-a-pet-is-proven-not-guessed.md) — *ownership was read off the log's possessive (`Kainos`s warder`), which works only while a pet's name contains its owner's. A **named** pet writes `Garn hits a coyote` — identical to a player — so [0067](./0067-the-meter-counts-your-party-s-fights.md)'s scope saw neither side as ours and **dropped the fight whole**: the damage went missing, not onto the wrong row, and a meter that is merely low looks like a quiet evening. - [0078: A fight records why it ended](./0078-a-fight-records-why-it-ended.md) — *[0036](./0036-a-fight-ends-on-death-not-a-lull.md) already tells a **resolved** fight (something died, short quiet closes it) from an unresolved one (enemy still up, long silence needed), computes which applied on every line, and throws the answer away — so 90 seconds ending in a kill and 90 seconds ending because the log went quiet read identically, though only one of them finished. Now stamped as `kill` / `death` / `timeout`, with the **later** of a kill and a death winning when both resolved it, plus `cut` for a fight the log didn't end at all (a reset, a flush). `cut` exists as a value precisely so **absent** can keep exactly one meaning — stored before this was recorded ([0021](./0021-stored-fights-keep-their-source.md)). - [0079: An unread line is counted by its shape](./0079-an-unread-line-is-counted-by-its-shape.md) — *a line no matcher claims is dropped in silence, and our tests can only pin grammar we already thought of — the same silence that left [0020](./0020-split-by-stance-and-invocation.md) dark against 243 stance lines that parsed fine and which nothing listened for. Unread lines are now tallied **by shape** (digits fold to `#`; nothing cleverer, since over-folding hides the gap), capped, reporting what it turned away so a truncated list can't pass as complete, and printed through `logging.ts` after a replayed gap. The half that makes it readable is the second bucket: chat, tells and other players' emotes are **matched and ignored** — counted, text discarded — so an evening of guild traffic can't bury the one line that reveals a hole, and the bulk of other people's words are never kept in the first place. Names are **not** folded and the ADR says so rather than over-claiming. Relatedly, the two hand-maintained "which kinds are combat" lists become one typed `isCombatEvent`, so omitting a new kind is a compile error instead of a silence*

- [0080: The game's own spell file](./0080-the-game-s-own-spell-file.md) — *the log says what you cast and what it did, never what it **cost**, so the most useful question a caster has was the one the meter couldn't answer. - [0094: A spawn timer is a window, not an instant, and the player sizes it](./0094-a-spawn-timer-is-a-window-not-an-instant.md) — *[0092](./0092-a-named-s-respawn-is-learned-from-your-own-kills.md) got the arithmetic right and then presented it wrong: one `dueAt`, a countdown, and **UP** — a soft measurement of a soft thing shown as an instant. Three things widen an observed gap and none is visible to any parser: a **placeholder** may be what actually popped (so the "respawn" is a cycle length times however many pops it took), a mob **walks** (up on time, nowhere near your camp for minutes), and **you are not a stopwatch**. All three inflate and none can shorten — which is exactly what makes the shortest-gap rule sound *and* what makes a single number a lie, since the bound is loose by an unknown amount. So **both ends of the evidence are kept**: `longestSeconds` beside `shortestSeconds`, because a long gap means little alone but next to the shortest it is the only measure of what the figure is worth. Past `ERRATIC_RATIO` (half again — a low bar, since a fixed respawn watched promptly produces gaps seconds apart) the **range leads** — `15m–45m, from 3 gaps` — because a reader shown `15m` camps to fifteen minutes however small the print is; and the caveat **names causes rather than a confidence score**, since each is actionable where a percentage isn't (camp the cycle, pad it, or kill it promptly a few times and it tightens itself). A timer now runs to a **window** (`watchFrom`, state `window` = *might be up*) and fires when the window **opens**. The load-bearing refusal: **we do not invent the lower bound** — nothing in the log says how early a mob might pop, and a fraction-of-the-estimate rule would be a guess in a measurement's clothes, the same mistake 0092 declined when it wouldn't recover a named from capitalisation. Padding is therefore **the player's, per mob, zero by default**, so with none set `window` never occurs and the behaviour is the old point-in-time countdown exactly. It **re-arms a running timer** ("this one keeps beating me to it" is a thought you have *while waiting*), is clamped to the interval (a window opening before the kill would be permanently open), and a window opened **retroactively is armed silently** — generalised into `arm()` so a replayed log gap, an import and a re-pad are one check rather than three. `due` became **`up`**, which means the by-time has passed, **not** that it's in front of you. Rejected: **averaging or a standard deviation** (the gaps aren't samples around the truth, they're the truth plus an arbitrary always-positive delay — their mean describes your evening, and the minimum is the only statistic with a meaning), **auto-detecting placeholders** (a wide spread fits a cycle and a player who wandered off equally well), and a **global padding setting** (padding is a property of a camp). A placeholder cycle still isn't modelled; `timerKey` is the seam it would go through*

- [0095: Your own DoT tick is yours, because the log says so](./0095-your-own-dot-tick-is-yours.md) — *[0071](./0071-a-dot-tick-belongs-to-whoever-cast-it.md) described **two** wordings for a damage-over-time tick, and there are **three**. The third is the one that says *your* — `A minotaur slaver has taken 29 damage from your Heat Blood.` — and neither pattern could ever match it: `DOT_FROM_RE` needs a trailing " by \<caster\>" to bind, `DOT_BY_RE` needs "damage by" where this says "damage from". So it fell through to the unparsed pile, **silently**, because an unread line is only ever a tally in a debug section. A sweep of a real 230,000-line log measured the cost: **1,737 lines, 27,775 damage — 3.3% of that character's whole output** across nine spells (Stinging Swarm 11,452, Heat Blood 7,413, Leech 4,448…), none of it duplicated anywhere else in the log; for a DoT-led character it is not 3% but most of what they do. Two findings shaped the fix. **A tick can crit**, tagged after the full stop exactly as a swing is (`… from your Stinging Swarm. (Critical)`) — so patterns anchored at the full stop missed them, and critical ticks are the *biggest* ticks in the log **by a factor of two** (84 against a plain 42): that anchor wasn't losing a few lines, it was losing precisely the ticks worth recording. And **the nameless wording still happens for your own spells** — `Infectious Cloud` appears 248 times as "from your…" and 12 times nameless on a mob, in a log where you cast it 21 times — so both halves are needed, the stated caster *and* 0071's correlation with your earlier cast. `your` is captured as the **attacker group** rather than special-cased, since `combatant()` already folds "you"/"your" to `SELF`: no new code path, and `casterUnknown` stays unset by the same rule the "by \<caster\>" form uses — which is load-bearing, because `dot-attribution` keeps only *one caster per spell name, last seen*, so a group-mate casting Heat Blood after you would otherwise take your ticks off you. **A stated caster outranks a correlated one**, the same precedence [0025](./0025-observation-over-the-wiki.md) gives an observation over a claim. **Forward only**: stored fights keep the figures they were written with ([0021](./0021-stored-fights-keep-their-source.md)'s rule), and re-derivation stays in todo rather than being invented to backfill one field. Consequences: every figure including your DoTs rises (838,608 where it read 810,833 on the log measured), and the scoreboard's **`biggest-tick` becomes reachable and stops being live-only** — [0093](./0093-a-high-score-is-a-personal-best-with-a-floor.md) shipped it as "only a live line can set this" when in truth *nothing* could, the line being unread; a damage cell whose hits are **all** ticks is a DoT, so the cell's own maximum **is** its biggest tick and a stored fight can seed it. Your own **damage shield** has the identical first-person problem one wording along ("by YOUR thorns" has no possessive for `SHIELD_RE` to bind) — 907 lines, 1,576 damage — left in todo as its own shape*

- [0096: Stored data says which rules wrote it, and a revision is not a build number](./0096-stored-data-says-which-rules-wrote-it.md) — *[0095](./0095-your-own-dot-tick-is-yours.md) raised every damage figure including your DoT ticks and was forward-only, so a thousand banked fights now under-report and **nothing on disk says so**. They don't look broken, they look like measurements — the worst way for data to be wrong, and the opposite of what this app rules everywhere else (show the doubt, [0023](./0023-kill-heatmap.md); say what a figure is worth, [0094](./0094-a-spawn-timer-is-a-window-not-an-instant.md)). Four version markers already existed, each invented where it was needed — the kill log's and settings' `schema`, the wiki's `CACHE_VERSION`, the gazetteer's `GAZETTEER_VERSION` — while five stores carried none and the committed generated datasets recorded nothing about what built them. Now every store writes a **`provenance` stamp** and one shared table names each body of data, its revision, and the remedy. **A revision is per concern and is emphatically not the app version**: CI stamps a build number into every push ([0064](./0064-every-build-has-a-number.md)), so comparing app versions would mark every store stale on every build and train you to ignore the flag — the same failure [0093](./0093-a-high-score-is-a-personal-best-with-a-floor.md) dodged by not celebrating a fresh board's first eight records. The build rides along in the stamp but is **never compared**; it's the answer to "which build wrote this" in a bug report. **Nor is a revision a schema**: a schema is what the app can repair *by itself, silently, at launch* (`migrations.ts`), a revision is what it **cannot** — re-read a log, re-run a script, refetch — so the honest move is to say so and let a person decide. A file carries both and bumping either does nothing to the other. Stamped in **`writeJson`**, one word per store, because a store that forgot would look permanently current and a silently wrong "up to date" is worse than no flag. The stamp is written **first**, which is load-bearing not tidy: the reader finds it in a **window from the head of the file** since a real history is megabytes, and getting that backwards (the spread put it last) made every large store report itself stale for ever — both halves commented, one test pinning it. An **unstamped file is assumed current** unless its concern says otherwise, or the day stamping ships every store screams about data that is fine; `combat-history` and `high-scores` are the two honest exceptions, 0095's bump predating stamping. Data from a newer build is **`ahead`, not stale, and offered nothing** — a downgrade must never rebuild newer data with older rules, the hazard [0031](./0031-an-inferred-bound-must-be-able-to-fall.md) guards from the other side. A **remedy names who can act**: only re-eat and refetch get a button, `script` prints the command, `rescan` says there's nothing to do, `unrecoverable` admits a peer's observations were never ours to re-derive — and the ones nobody can act on aren't counted in the badge, or it'd be a count you can never clear. Settings → **Recorded data** shows every row including the current ones, since a panel that renders nothing when all is well is indistinguishable from a broken one. **A bug found on the way and fixed here**: `kill-log.ts` never read or wrote `schema`, so the first save after a migration *deleted the migration's stamp* — the migration then re-read **every log in the folder** (19 MB) to repair nothing, every launch, for ever. A store must write back fields it doesn't own; pinned by a test, and precisely the failure the "stamp in the shared writer" decision exists to prevent*

- [0097: A sighting is the tightest evidence there is, and a timer is silent until asked](./0097-a-sighting-is-the-tightest-evidence-there-is.md) — *[0092](./0092-a-named-s-respawn-is-learned-from-your-own-kills.md) learns a respawn from the gap between two kills and [0094](./0094-a-spawn-timer-is-a-window-not-an-instant.md) admits how loose that is; neither noticed that a kill gap is the **loosest evidence obtainable**. Between the spawn and your second kill line sits how long before you looked, how long to get there, how long to kill it, and however many placeholder cycles went by — none of which the log can see. The player can: they are sitting there looking at the mob. So **marking it up is a measurement**, `R ≤ now − killedAt`, through the same ratchet (shortest wins, implausible discarded not clamped) and stored rather than derived, since it's the one fact only the player can supply. `RespawnSource` becomes `stated | seen | killed` and the estimate is just the smallest bound — a sighting usually wins but is **not privileged**, because preferring it over a tighter kill gap would be discarding evidence to protect a label. **`alive` outranks the clock in both directions**: before the window (finding it early is exactly what proves the timer too long) and long past stale (it *is* up; time doesn't change that) — [0025](./0025-observation-over-the-wiki.md) pointed at our own estimate, where `up` is what we guessed and `alive` is what you saw, and the screen must never show them alike. An alive mob never alerts: you're looking at it. Separately, **notify goes per mob and off by default** — tracking is automatic and camping is deliberate, so the set you want to hear about is always far smaller than the set being timed, and a tool that interrupts about things you didn't ask for gets muted wholesale, costing you the one alert you wanted. And the mirror: **`markDead`** starts or restarts a countdown by hand — for when the app wasn't watching, a camp changed hands, or a pull went unlogged — seeding a clock while teaching the estimate nothing (one death measures no respawn) and never touching the kill log. Behind all of it one rule the panel had broken in three places: **every state a player can set, they can unset** — a typed figure could only be cleared by emptying the box and saving, which works and which nobody discovers, while "not a named" removed the row carrying its own undo. So an editor with a value shows an explicit **Clear**, dismissals are listed under **Not tracked** with a count, and each "tell the tracker what's true" button has its opposite within reach. A timer can also be **typed in** (`add`), which turned out to answer "custom timers" too — by not distinguishing them: a label no kill line matches simply never restarts itself, so a boat or a raid lockout works with no branch about what a row *is*, while a name that is a mob starts learning the moment you kill it. Only a hand-added row can be **removed**, without ceremony (it's exactly what you typed), and a learned one offers no remove because it would come straight back. A sighting also arrives **without being clicked**: a **consider or a hail** means the same thing and comes free from what a camper does anyway (you con a named before you pull it), routed through `markUp` itself so the automatic and manual kinds can never diverge. Two guards, both because this feeds a ratchet: it reaches only a timer **already counting down** (so everything you look at on the way to a camp is silent, and there is a `killedAt` to measure from), and the consider **vocabulary is a closed set that fails closed** - EQ's regard phrases are faction, so matching the list rather than "anything before a `--`" is what stops group chat with a dash reading as a sighting; an unknown wording costs one click, a false one is permanent. Rejected: a **global** notify (which mob you're camping is the whole question), **inferring** a sighting from the log (no such line, and a guess here can't be withdrawn), and reading a sighting as a **lower** bound (not having seen it isn't evidence it wasn't there — that's 0094's wandering problem again)*

- [0098: A mob is a thing you hunt, not a thing that drops](./0098-a-mob-is-a-thing-you-hunt.md) — *the shopping list holds **items**: a name a loot line can match, a count needed, a count held — and everything downstream assumes it. A mob is none of those. "+ Add" on a mob page had already been repaired once (the search results used to add any non-quest page as an item, so a named landed on the list as something to loot); the fix ruled a mob a **source** and added its loot table instead. Still wrong, as the spawn-timer work made obvious: a named is a thing you go and **kill**, so adding *Ghoul Lord* should put Ghoul Lord on the list. Instead you got a dozen unasked-for item rows (a mob page keeps its drops in `components`) or, with no loot listed, silently nothing. So the list could express "the twelve things this mob drops" and could not express "this mob". Now an entry has a **`kind`** (absent = `item`, so nothing on disk changes meaning), a mob **adds itself** whatever the wiki knows about its drops, and it is excluded from loot matching **by kind rather than by luck** — left in, the default substring match credits "Ghoul Lord" with the Ghoul Lord's Cape. It is never an outstanding item either, or it would sit pending for ever, inflating every "what's left" count. On the Hunt list it's a **target placed by your own kills**, because a mob's wiki page has **no sources at all** — [0025](./0025-observation-over-the-wiki.md) from the other side: not "observation corrects the wiki" but "the wiki never knew". A mob you've never killed is listed under an unknown zone rather than dropped, and a target **leads its zone** and counts as a reason to go there, or a zone whose only draw is the named you asked for would sort to the bottom of the page it exists to top. Rejected: a **separate hunt store** (two lists, two shares, two places to look — it needed a kind, not a sibling) and **keeping the drops too** (that's the complaint, not a compromise). Not modelled: how many you want to kill*

- [0099: A countdown can stay on screen, and a timer picks a saved look](./0099-a-countdown-can-stay-on-screen.md) - *spawn timers reached the screen exactly one way: a banner at the pop. That answers "it is up **now**", once - and the question a camper actually asks is **"how long left"**, constantly, mid-pull, with the only answer on a tab you had to alt-tab out of the fight to read. So a timer can be **pinned**, per timer and opt-in, onto the existing `/alert` overlay: everything that makes that window right for a banner (frameless, transparent, always-on-top, click-through) is what a countdown wants too, and a second window would be a second lot of window state to place and remember ([0074](./0074-how-a-window-was-left-is-window-state.md)). Opt-in because tracking is automatic - every named you walked past would be a wall of text, not a glance - and kept **separate from notify** on purpose: one is a *moment*, the other a *dial*, and a camper very often wants the clock and no banner at all. Each countdown **sits where its own alert would** — same style, same position, custom placed spots included — which pushed `placement` out of the banner into shared `alertPlacement` and the six position rules onto an `.overlay-at` class both wear, one setting with one definition. Resolved **in the renderer from the id**, the opposite of a banner and deliberately: a banner is frozen when it fires, a readout should move the moment you restyle it. Where the two now commonly collide the **banner draws over** and leaves by itself. Colour marks the row's edge (which alert this is) while the *clock* keeps the state vocabulary, since "up" and "waiting" must stay tellable apart whatever colour was picked. It draws its own dark backdrop, since it floats on a transparent body over whatever the game is showing, and sets `pointer-events: none` so a read-only list never takes a click back. Separately, the pop now **wears a saved style or the defaults, never its own look** - the same call [0093](./0093-a-high-score-is-a-personal-best-with-a-floor.md) made for a celebration, because a per-timer editor would be the third source of truth [0086](./0086-editing-a-shared-style-from-a-rule-forks-it.md) and [0090](./0090-one-style-editor-at-a-time.md) exist to prevent; resolved in main and sent *with* the alert, since the overlay knows only the defaults, and a deleted style falls through to them rather than losing the banner. The picker shows only when Notify is on, a look for a banner nothing will raise describing nothing. The app also **ships two looks** rather than leaving both to the defaults: a cast alert is a *warning* and keeps the red, while a record and a spawn are *news* - a gold **Record** (no flash) and a green **Spawn timer** (top-right, lingering, since a pop is news you may be seconds late to notice). Ordinary saved styles, in the Alerts list, editable and deletable - a built-in the player couldn't reach would be a second wardrobe by another name. Seeded by a **migration**, not a defaults merge, since `deepMerge` replaces arrays wholesale (right for a list the player curates, wrong for one the app also contributes to): `seedBuiltInStyles` reconciles by **id** and is deliberately not schema-gated, because the question it asks is its own answer. Rejected: showing **every** running timer, a **placement control of its own** (it inherits the alert's), a **fixed corner** (what shipped first - a fact about the layout, not about the player), and giving the HUD **a wardrobe of its own** (it borrows the alert's - a readout and the banner it precedes are the same thing at two moments)*

## Open Questions

- **Can a celebration exist without a number to beat?** The scoreboard
  ([0093](./0093-a-high-score-is-a-personal-best-with-a-floor.md)) is built entirely on *magnitude*: a
  category, a figure, a floor, and a previous value to clear. A sweep of a real log turned up two
  moments that plainly deserve a banner and have **no figure at all** — `You have been knocked
  unconscious!` **survived** (26 knockouts in three weeks, 4 of them lived through), and killing a
  **named** (27 distinct). Neither is a personal best; both are the best stories in the log. Either the
  board grows a second kind of row — a *moment*, counted rather than measured — or these belong to a
  separate feed and the scoreboard stays strictly about magnitudes. Worth settling before either gets
  built, because the answer decides whether `HighScore` gains an optional value or a sibling type does.
  Both candidates are written up in [ideas.md](../ideas.md) `## More high scores`.

*The three below came out of reading the other EQ Legends tools ([neighbours.md](../neighbours.md));
the work they'd unblock is in [todo.md](../todo.md) `## From the neighbours, second pass`. The
fourth — whether to read installed game files beyond `maps/` — was **settled by
[ADR 0080](./0080-the-game-s-own-spell-file.md)**: yes, bounded to the columns a patch can't move,
and degrading to blank facts when the file isn't there.*
- **Is a second reference source worth taking from a different game?**
  [ADR 0003](./0003-eqlwiki-runtime-data-source.md) chose eqlwiki because it is *this* game's wiki. The
  Project Quarm distillation a neighbour ships is richer than the wiki on the three things we most want
  seeded — named spawn points, respawn timers, drop percentages — and is EQL's lineage rather than EQL.
  [ADR 0025](./0025-observation-over-the-wiki.md) already says observation outranks the wiki, so the
  machinery for "shown as a claim, overruled by what you saw" exists. Against it: the wiki is at least
  *edited by people playing this game*, and a wrong number from a sibling game is wrong in a way no
  amount of careful labelling makes the player's problem less annoying. Also a licensing question, not
  just a design one.
- **Does a dungeons-only guide line reopen in-zone routing?** ADR 0049 was retired and
  [ADR 0062](./0062-a-travel-graph-of-zone-lines.md) narrowed the map's non-responsibility to "no
  routing inside a zone", because an `L` record is a wall in a dungeon and a contour outdoors, so a
  drawn route is a guess dressed as advice. A neighbour ships one anyway and it doesn't refute the
  objection — it paths *along the drawn lines*, which parallels a corridor and traces a hillside. But
  the objection is really about *outdoors*: where the geometry is known to be walls, the guess is
  sound. If we end up reading `spells_us.txt` we get `zone_type` (outdoor/dungeon) for free. Is a route
  that refuses to draw outdoors a different enough claim to be worth costing, or does a feature that
  works in half the world read as broken in the other half?
- **Should interface scale grow as well as shrink?**
  [ADR 0026](./0026-interface-scale-only-shrinks.md) caps at 100% — the overlay's job is to take less
  of the screen, and a magnified overlay is a bigger thing between the player and the game. Two
  neighbours ship the opposite hard: presets at 100 / 200 / 250%, with layouts that grow rather than
  clip, offered in the same menu as the theme. They are serving the same players we are, and EQ's
  audience is twenty-five years older than it was. Is our cap a considered stance or an untested
  assumption?

- **OCR beyond item lookup — is a live health trace wanted?** It's ruled out for the **experience
  bar** (the log's gains plus a level-up baseline solve it exactly,
  [ADR 0017](./0017-camp-efficiency-and-asking-the-player.md)) and for **mana cost** (the wiki states
  it — see [ideas](../ideas.md)), and **maximum health** is now *inferred* from what you survive
  ([ADR 0018](./0018-inferred-max-hit-points.md)). So the only prize left is a health trace rather
  than a maximum, and it needs a user-calibrated screen region per UI layout, is fragile across
  resolutions and UI mods, may capture nothing in exclusive fullscreen, and a confidently wrong
  reading is worse than a blank.
- **Items per kill, alongside the drop chance.** `drops` counts kills that produced an item, which is
  the right numerator for a probability but throws away the stack size — "You looted 2 Spiderling
  Eye" counts once ([ADR 0024](./0024-mob-knowledge.md)). For a stackable trash drop the useful
  figure is items-per-kill. It's a second number rather than a correction, and it changes the shared
  observation shape, so it wants deciding rather than sneaking in.
- The app now reports its peer connection truthfully, but **nothing displays it**
  ([ADR 0070](./0070-a-dropped-room-rejoins-itself.md)): the map's `connected` is the
  `connectPeers` *setting*, and the only consumer of the real status is the room clearing itself.
  During an outage a player sees the user list empty and their pings stop landing, with nothing
  saying why. Is that worth a real connection light, or is a silent self-heal the right amount of
  noise for a game overlay?
- A recovering peer re-joins under a **fresh peer id**, so the room sees a stranger arriving rather
  than a return ([ADR 0070](./0070-a-dropped-room-rejoins-itself.md), on ADR 0011's "the id is
  transport-only"). Cheap today; if reconnects prove frequent it reads as churn in the 👥 panel.
  Should a session keep its id across a recovery?
- A succor point can be **read** off a map and never written down
  ([ADR 0069](./0069-a-succor-is-a-port-inside-one-zone.md)), because `TravelPlace` carries no
  coordinates and an unplaced safe point is a guess that can beat a measured walk. Should a
  hand-authored place be able to state a `/loc` — which would also let `manual-links.ts` place the
  docks it currently has to invent?
- The `fuzzy` tier of `resolveZone` currently fires on **nothing** across all 344 shipped zones
  ([ADR 0068](./0068-a-zone-name-resolves-against-what-we-know.md)) — every name it could reach,
  the three tiers above it already reached. Is a last resort that has never spoken worth carrying,
  or should it wait until a source we don't yet read gives it something to do?
- Should the Damage tab **say** whose fights it's counting — a line naming the party it
  believes you're in ([ADR 0067](./0067-the-meter-counts-your-party-s-fights.md))? The filter is
  always on and silent, so a group line the server words differently than we expect looks like
  a meter that's merely quiet about a group-mate. Against it: the roster is evidence, not truth,
  and showing it invites reading it as the game's own group window.
- A line watch is a substring of the whole log line, and nothing rate-limits it
  ([ADR 0050](./0050-a-watch-can-read-a-whole-log-line.md)). A careless one ("hit") fires
  thousands of times a night. Is the overlay's four-banner cap enough, or does a watch want a
  cooldown — and if so, per watch or per matched sentence? Two later decisions sharpen it without
  answering it: a delay ([ADR 0082](./0082-an-alert-can-be-scheduled.md)) means such a watch now
  *queues* its noise instead of merely making it, and conditions
  ([ADR 0084](./0084-a-watch-is-a-rule-not-a-substring.md)) give a careless watch a way to be
  narrowed rather than throttled — so a cooldown would have to say whether it gates the match or the
  firing, and whether narrowing is simply the better answer.
- Open Relay's community TURN is best-effort and not production-grade
  ([ADR 0046](./0046-our-own-ice-servers-not-peerjs-defaults.md)). Is peer sharing worth
  running our own TURN for, or is "works for most, fails for symmetric NAT" acceptable?
- Pooled mob knowledge is attributed and forgettable, but unweighted: every peer counts the
  same. Should contributions be weighted, or individual peers mutable/vetoable?
  See [ADR 0024](./0024-mob-knowledge.md).
- Coin per mob pools with peers; an item's vendor price does not
  ([ADR 0047](./0047-money-is-copper-in-two-ledgers.md)). A price is the easiest thing of all to
  pool — it's the same for everyone, so one observation settles it — but it isn't in the
  observation payload. Worth adding, or is "what you've sold yourself" the honest scope?
- A zone's difficulty rides inside its name, which keeps it out of the stored shapes and the peer
  payload ([ADR 0057](./0057-a-grade-is-not-an-identity.md)). Now that a variant is no longer its
  own sample ([ADR 0059](./0059-a-zone-s-variants-are-one-zone.md)), a camp report that wanted to
  compare difficulties would have to read them off the *records* before they age out. Is that worth
  a field of its own, or is "Blackburrow 3" in the name enough for a player reading their own
  history?
- Undocumented drops are surfaced per mob. Should they also be *reported upward* somewhere —
  a shared list of "things this build drops that no wiki knows"? The room already pools
  observations ([ADR 0024](./0024-mob-knowledge.md)); this would be the useful summary of them.
- Should out-of-era pages be *hidden* (not just badged)? Filtering search results by
  era would need a category lookup per result — flagging-on-open is done today.
- Should the overlay support multiple named lists / profiles per character?
- Should the damage meter break a fight down by *phase* (adds arriving, mob enraging)?
  Today a fight is one flat window from first swing to last.
- Should a fight's stored record keep the raw `logId` range it covered, so a past fight
  could be re-derived from the log if the tracker's maths changes?
  See [ADR 0019](./0019-parse-once-and-one-tracker.md).
- Should the overlay toggle hotkey be user-configurable? (Currently a fixed
  `Ctrl/Cmd+Shift+O` via Electron's built-in `globalShortcut` — no native dep.)
